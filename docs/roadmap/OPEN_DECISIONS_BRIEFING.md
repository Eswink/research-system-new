# 待拍板决策简报（Open Decisions Briefing）

**这是给用户的决策入口，不是待办清单。** 本文件只**汇总与选项化**：每一项给出「要决定什么 /
选项 / 每选项的影响面与代价 / 证据出处 / 不做会怎样 / 建议」。**本文件不实施任何一项** ——
没有代码、配置、门禁、策略面、依赖 pin 或运行时默认值因它而改变。

- 来源：GOAL-008…GOAL-015 记录里的「不进入循环 / 需人工拍板」条目 + 各 RECHECK 的残余登记。
- 口径：**决策项（D-NN）**= 需要你拍板；**标准禁令（standing）**= 已经写明且无需拍板的边界；
  **已了结**= 已经执行完、无待办。
- 机器校验：`tests/tooling/test_pending_decisions_briefing.py` 强制「本文件 ↔ GOAL-015
  「不进入循环 / 需人工拍板」节」**双向对齐**，并要求每项六要素非空（删一项即判红）。

## D-01｜出厂组合根是否自己接执行体缝（`M-1`）

- **要决定什么**：`ApiDeps.tool_providers`（执行体缝）在**出厂组合根**里是否应该由产品自己接上，
  而不是像现在这样生产路径为空字典、由**装配方**（测试/live 支持模块、部署方）补执行体。
- **选项**：(a) 出厂组合根自己接一份默认执行体；(b) 维持现状（缝由装配方补），但把「缝的契约」
  写成机械判据（缺执行体时 preflight 必须**点名**哪个能力没人执行）。
- **影响与代价**：(a) 让「出厂即可跑」成立，但会把一条**真实执行面**带进默认装配（安全面变大、
  Fake 与真实执行体的边界要在组合根处重新划清）；(b) 现状语义清晰、安全面不变，代价是
  「出厂组合根跑不通带执行体的协议」需要文档与判据讲清楚。
- **证据出处**：GOAL-014 迭代日志 cycle 6（`M-1` 仍由装配方补执行体）；`RECHECK-20260924-162`
  第一节；`MEM-20260924-125`（「缝为空」的三种含义）。
- **不做会怎样**：装配方各自决定怎么补 ⇒ 「同协议两套装配」的老问题可能以新形态回来。
- **建议**：**取 (b)** —— 先加一条判据把「缺执行体必须点名」钉住，等 D-11 的开关语义定下来再谈 (a)。

## D-02｜读类能力是否**成类**预放行

- **要决定什么**：策略面上被登记为「该登记」的读类能力（`citation.inspect` / `experiment.read` /
  `provenance.read` 等 15 条）是否应该**成类**预放行，还是维持逐条放行。
- **选项**：(a) 成类 (`read.*` 一条规则覆盖)；(b) 维持逐条（需用时单条放行）；(c) 不动。
- **影响与代价**：(a) 少一条条放行的摩擦，但把「默认 deny」（AGENTS.md §9）的粒度从能力级降到
  类别级，一次误判影响面更大；(b) 每次新增读能力要走一次授权，摩擦固定但影响面最小；
  两者都不改变 `default_effect: DENY` 本身。
- **证据出处**：`docs/architecture/POLICY_SURFACE_AUDIT.md`（差集表：该登记 15 条）；
  GOAL-014 EC-03 的差集审计与「该放行 0」结论；`GOAL-014` 授权第 (2)/(6) 条。
- **不做会怎样**：新增读能力会反复撞 `default_effect`，每撞一次就是一次 GOAL 级授权；
  但没有任何**当前**阻塞（协议可达面 8/8 已被非 deny 规则覆盖）。
- **建议**：**取 (b)** —— 维持逐条。成类预放行属「`W-A` 之外的策略面放宽」，需要单独论证。

## D-03｜依赖 pin 升级（`R-D1`）

- **要决定什么**：是否升级 23 条 Dependabot 告警涉及的依赖（4 high / 13 moderate / 6 low；
  包分布 `vite` 14 / `undici` 8 / `yaml` 1），以及升级的批次与验收口径。
- **选项**：(a) 一次性全升到已修复版本；(b) 分批：high 先升、minor/patch 合批，每批跑全量门；
  (c) 维持现状并登记豁免。
- **影响与代价**：(a) 告警清零最快，但 `vite` 在主版本内跳动可能影响 web 构建与设计基线快照；
  (b) 风险可控，代价是多个 cycle 的验证成本；(c) 零成本，但 4 条 high 会长期留在仓库告警面。
- **证据出处**：GOAL-014 EC-04 的现测（`scratch/goal014-c4-residual-probe.txt`）；
  `git push` 时上游返回的 23 条告警（4 high / 13 moderate / 6 low，2026-09-25 实测）。
- **不做会怎样**：供应链告警持续存在；每条都有 `first_patched_version`，但**不动 pin 是当前
  明文禁令**（GOAL-015 `escalation_triggers`），所以不拍板就永远不动。
- **建议**：**取 (b)** —— 先升 4 条 high（若它们都在 patch/minor 范围内），每批单独 cycle 验证。

## D-04｜hook 侧 L3 检测层

- **要决定什么**：是否给本地 hook 面装「L3」检测层（Mimosa 的语义检测层），以及装哪些、
  在哪个环节阻塞。
- **选项**：(a) 装检测层并把命中设为**阻塞**；(b) 装但只告警；(c) 维持现状（失败开放）。
- **影响与代价**：(a) 治理面最强，代价是 false positive 会阻塞提交/推送（本仓已有多次误报记录：

## D-11｜live 判据的开门条件 = 环境恰好有凭据

- **要决定什么**：`requires_live_llm` 的 live 用例当前的开门条件是「出厂端点目录声明 + 环境里
  恰好存在 `LLM_MAIN_KEY`」；是否改成**显式开关**（例如 `RESEARCHOS_LIVE_E2E=1`）。
- **选项**：(a) 加显式开关：凭据在场不再是充分条件；(b) 维持现状（凭据在场即跑）；
  (c) 维持现状但收紧为「开关 + 凭据」双条件（等价于 a 的更严版本）。
- **影响与代价**：(a) 默认门不再因**环境里有什么**而改变行为（可重复性上升），代价是 live
  作业要多设一个变量；(b) 零改动，但**任何人**在环境里放一个（哪怕是无效的）凭据都会让默认门
  变成真出网、并把语义从「跳过」变成「失败」；(c) 最严，但要求 live 作业改口径。
- **证据出处**：2026-09-25 CI 实测（run `36048265860`，`quality-ubuntu-latest`）：
  `tests/e2e/test_run_chain_retrieval_live.py::test_live_run_chain_retrieval_lands_a_real_identifier`
  **没有 skip**，带一个无效令牌真的调了出厂端点 ⇒ `AuthenticationError: Invalid token`
  ⇒ 该 job 判红；同一提交在本机（凭据有效）**通过**。归因：`_live_credentials()` 只判
  「环境变量在不在」（`tests/e2e/test_run_chain_retrieval_live.py:91`）。
- **不做会怎样**：默认门的结论继续取决于**环境里有没有凭据**——这正是「质量门可信度」缺口的
  一类；CI 上只要有人配了一个过期 secret，默认门就会红且**真的出网**。
- **建议**：**取 (a)** —— 加显式开关；并把「凭据在场」降级为必要条件而非充分条件。

  作业**、或维持现状只做「偶发红 ⇒ 复跑」的处置。
- **选项**：(a) 维持阈值与作业不变，把「偶发红 ⇒ 复跑 + 登记」写成协议（**本 GOAL 的实际做法**）；
  (b) 把该项拆到独立 job（不与其余 4400+ 用例同进程排队）；(c) 改成相对量（如与基线同进程对照、
  或用 allocation 计数而非 RSS）；(d) 提高阈值（**不建议**，等于放宽判据）。
- **影响与代价**：(a) 零改动、判据强度不变，代价是**偶发红**会污染一次 CI 结论（需要人工复跑 +
  登记）；(b) 需要 CI 作业结构改动（workflow 面），换来稳定；(c) 需要重写判据的测量方式
  （测量语义可能改变，要重证「非恒真」）；(d) 会让「内存泄漏」这类真问题更难被抓到。
- **证据出处**：**2026-09-25 实测** —— push `f4d98e6` 的 M0 run `36071654181`：
  `quality-windows-latest` **判红**，判词 `AssertionError: RSS grew 174.0 MiB (leak suspected)`
  （`assert 173.9921875 < 128.0`，`tests/observability/test_telemetry_overhead.py:150`）；
  **同一 run 第 2 次尝试（`run_attempt=2`）该 job `success`**；同一提交的
  `quality-ubuntu-latest` 与 CodeQL **全绿**；同一测试在本机 m0（22/23 的两轮）**全绿**。
- **不做会怎样**：同一类「在同一进程里量整进程 RSS」的判据会继续在**负载高**的运行器上偶发判红，
  每次都要人工复跑 + 归因（本 GOAL 这类工作已经发生一次），且**红绿不一致会削弱本地/CI 结论的
  可信度**——正是本 GOAL 要处理的那一类问题。
- **建议**：**取 (a) + 后续评估 (b)** —— 先按 (a) 的协议处置（判据与阈值**一字不动**），
  若同类偶发红再出现 ≥ 2 次，就按 (b) 把该项拆到独立作业；**(d) 不建议**。
