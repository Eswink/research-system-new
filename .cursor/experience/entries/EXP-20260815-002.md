# docker-py `wait(timeout=)` 超时异常类型跨平台不一致：改用 inspect 轮询 + deadline

## Problem

- 现象：DockerExecutionBackend 用 `client.api.wait(container_id, timeout=step)` 实现命令级 timeout，在 Windows npipe transport 下超时抛 `requests.exceptions.ConnectionError`（底层链：npipesocket `TimeoutError` → urllib3 `ReadTimeoutError` → requests `ConnectionError`），而不是 Linux unix socket 上预期的 `ReadTimeout`；`except ReadTimeout: continue` 捕获不到，执行链路直接崩溃。
- 上下文：M9 容器执行后端 timeout 路径；Windows 10 + Docker Desktop（linux 容器，daemon 29.2.1）；docker-py 7.2.0。
- 影响：timeout 语义（M5 D2：TIMED_OUT 状态化而非异常）在 Windows 上失效，容器 E2E timeout 测试无法通过。

## Solution

- 根因：docker-py 在 Windows 走 npipe transport，其 socket 超时异常与 Unix transport 类型不一致（npipesocket.py 抛原生 TimeoutError，requests 层包装为 ConnectionError）；仅捕获 ReadTimeout 的平台假定不成立。
- 解法：不依赖 `wait(timeout=)` 的异常类型，改用 `inspect_container` 轮询 `State.Running` + `time.monotonic()` deadline：Running=False → 正常退出；越过 deadline → timed_out（随后 `api.kill`）。纯 API 调用无平台分支，单元测试（stub 轮询序列）与容器 E2E 双验证通过。
- 被拒方案：`except ReadTimeout: continue`（Windows npipe 抛 ConnectionError，捕获不到）；扩大 except 到 ConnectionError（掩盖真实连接故障，不可行）。

## Evidence

- source_refs：本会话修复前 E2E 失败输出（ReadTimeoutError → ConnectionError 完整链路）；修复后 `test_docker_backend_unit.py` 17 PASS（轮询序列/超时 kill/清理断言）+ `test_docker_backend_e2e.py` 10 PASS（Windows 实跑）+ 容器 contract 6 PASS；m0 profile 全绿。
- 如何失效：docker-py 升级修复 npipe 超时异常类型后，wait(timeout=) 方案可重新评估；Linux 侧行为（ReadTimeout）未在本会话实测，仅按 docker-py 文档/源码推理。
