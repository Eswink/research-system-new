# git commit 前核对暂存区范围；push 的 stderr 红字不是失败

## Problem

- 现象 1：执行 `git commit -F <msg>` 时发现**提交了整个暂存区**——之前的白名单 `git add` 已暂存两个语义单元的文件，一次 commit 把全部内容并入一个 commit，语义单元混淆。
- 现象 2：`git push origin main` 在 PowerShell 下显示红色 "git : To https://github.com/..." 与 NativeCommandError 样式输出，看似失败，实际 push 成功（`d439c50..b11e35b main -> main`）。
- 上下文：Windows PowerShell + git；本会话 M12-R1 收口提交 2 个 commit。
- 影响：commit 语义单元错误需 `git reset --soft` 重做（未 push 前可行）；push 红字误报会误导判断。

## Solution

- 根因 1：`git commit` 默认提交**全部暂存区**；多个语义单元已同时暂存时，一次 commit 无法区分。
- 根因 2：git 的进度/远端信息走 **stderr**，PowerShell 把 stderr 渲染为红色并包装成 NativeCommandError（`2>&1` 合并时更明显），不代表命令失败。
- 解法（稳定模式）：
  1. commit 前先 `git status --short` 核对暂存区（`A`/`M` 前缀）确实只含本语义单元文件；
  2. 多语义单元必须**逐单元暂存→提交**（add 一批 → commit → 再 add 下一批），或用 `git restore --staged <path>` 把错暂存路径移出；
  3. 已错误合并且**未 push** 时：`git reset --soft HEAD~1` + `git restore --staged <path>` 拆分，不产生破坏（软重置只动 index/HEAD）；
  4. push 后验证用 `git ls-remote origin <branch>` 或 `git status` 的 "up to date" 行，不依赖 push 输出的红字/绿字。
- 被拒方案：`git reset --hard`（丢弃工作区改动，本仓库规则禁止）；push 后才发现错误（已公开历史不可改写）。

## Evidence

- source_refs：本会话实际执行序列（第一次 commit 合并全部暂存 → reset --soft 拆分 → 两个语义单元 commit `2e312f3` + `b11e35b` → push 成功，`ls-remote` 确认远端头一致）。
- 如何失效：当 git 配置改变 stderr 输出或使用 GUI 提交工具时本条部分不适用；核心语义（commit 前核对暂存区）始终有效。
