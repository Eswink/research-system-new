# 标题：全套 pytest 与 pnpm run check 并行时批量 E 类失败，串行复跑全绿

## Problem

- 现象：`uv run --frozen --no-sync python -B -m pytest tests/api tests/architecture tests/contracts tests/application tests/adapters tests/evals tests/domain -q` 与 `pnpm run check` 在同一会话同时后台启动，pytest 进度在 10%-57% 区间出现大量 `E`（约 30+ 处），无具体错误细节可见（-q 输出仅进度点）。
- 上下文：Windows PowerShell、项目冻结 uv 环境（.venv）、提交前验证阶段；两个任务均由本会话并发启动。
- 影响：阻塞提交前验证结论；首次判断时无法区分环境问题与真实代码失败，需分块重跑定位。

## Solution

- 根因：推断为并行执行竞争（CPU/IO/共享 sqlite 测试资源争用或 hook 观测竞争）；"单次观察，未经独立复现"——机制未直接观测，但同一测试集在独占串行执行下确定性通过。
- 解法：验证/冒烟类重负载任务串行执行，不与其他长任务（pnpm run check、其他 pytest 进程）并行；分批验证时保持同一冻结环境与同一目录集合，结果可对比。
- 被拒方案：并行重试（会复现竞争，浪费约 3 分钟）；把 E 当作真实失败逐项诊断（在串行复跑全绿后已排除）。

## Evidence

- source_refs：本会话两次运行对照——并行运行 10%-57% 满屏 E（用户终止）；串行复跑同一测试集 1381 passed, 2 skipped, exit 0（约 189s）。此前分块验证（api+architecture+contracts 322 passed；application+adapters+domain 955 passed；evals 104 passed）与串行全套一致。
- 如何失效：当测试资源完全隔离（独立工作区/容器/CI 分机）、或测试不再共享 sqlite 临时文件等资源时，本条可能不再适用；若确认某具体 E 是真实失败而非竞争，应以该失败为准。
