# 安全门禁 hook fail-closed 拦截 MCP 调用：不重试、不改 hook，改用替代工具并报告 capability unavailable

## Problem

- 现象：MCP 工具调用被仓库安全门禁 hook 以 fail-closed（失败即阻断）方式拒绝，
  报错：`安全门禁缺少有效的 tool_name/tool_input 字段，已按 fail-closed 拒绝 MCP 调用`。
  实测命中两个 MCP 服务：`cursor-ide-browser`（browser_tabs）与
  `cursor-app-control`（rename_chat）。
- 上下文：2026-08-21 工具能力测试会话；调用参数已按各工具 JSON schema 核对
  （如 `browser_tabs` 的 `{"action": "list"}` 为合法必填参数），非参数格式错误。
- 影响：浏览器控制与应用控制两类 MCP 能力在会话内完全不可用；系统 sessionStart
  提示该 error_signature 已跨 ≥2 次会话出现（occurrences=2）。

## Solution

- 根因（2026-08-21 后续确证，确定性证据）：`mcp_guard.py` 的 `beforeMCPExecution` 解析 bug——
  Cursor 3.16.29 实测该事件参数字段为 `tool_input` 且值是 **JSON 字符串**
  （`"{\"action\":\"list\"}"`），而 hook 原代码要求 `tool_input` 为 dict，
  且不识别官方文档所称的 `arguments` 字段 → 所有 MCP 调用命中 fail-closed 拒绝。
  （官方文档称参数字段为 `arguments`，与实测字段名不一致；hook 需双字段兼容。）
- 解法：
  1. 修复 hook 解析：`_parse_tool_input` 同时接受 `arguments` / `tool_input`
     两个字段名，以及 dict / JSON 对象字符串两种形态；空字符串视为空参数；
     解析失败与字段缺失保持 fail-closed deny；敏感扫描与外部调用 ask 语义不变。
  2. Hook eval fixtures 覆盖两种字段名 × 两种形态，并新增空参数/非法 JSON/
     缺 tool_name 边界用例；`security.yaml` 同步官方形态。
  3. 遇到拦截的代理行为约定：不重试同一调用（同签名必败）、不修改/绕过 hook，
     先用替代工具（WebSearch/WebFetch/Read/Grep/Ls/Shell）完成意图，再向用户
     报告为仓库 hook 问题；hook 属仓库代码，可在仓库内修复（无需用户改 Settings）。
- 被拒方案：反复重试同一 MCP 调用；通过关闭 guard / 改 hooks.json failClosed
  绕过安全门禁；把拦截误判为 MCP 服务故障而去诊断服务本身。

## Evidence

- source_refs：本会话 2 次拦截输出（browser_tabs / rename_chat 的
  permissionDenied 消息，均指向同一安全门禁 hook）；sessionStart 跨会话
  ≥2 次提示；同一会话内 WebSearch/WebFetch/Read/Grep/Ls/Shell 替代路径全部成功。
- 后续确证（确定性证据）：临时 dump hook 捕获 Cursor 3.16.29 真实
  `beforeMCPExecution` payload，确认 `tool_input` 为 JSON 字符串且无
  `arguments` 字段；`mcp_guard.py` 修复后 `run_cursor_hook_evals.py` 全绿
  （HOOK EVAL PASS）、governance validator 通过、真实环境 browser_tabs 调用
  成功返回。
- 如何失效：Cursor 版本将 `beforeMCPExecution` 参数字段改回 `arguments` 且
  为 dict、或新增第三个字段名时，`_parse_tool_input` 的兼容清单需更新；
  建议按 Cursor 升级节奏重跑 `run_cursor_hook_evals.py`。
