# 前台 uv run 长时命令通道超时返回 CURSOR_ERROR（命令仍在执行）；死锁探针挂起需 kill + pg_terminate_backend

## Problem

- 现象：本会话（M14 独立复审 + 修复轮）113 条工具失败中 7 条 Shell CURSOR_ERROR
  时长 >60s：5 条 ~67s（`uv run --frozen --no-sync python -B -m pytest tests/postgres -q`
  前台执行）、1 条 262s（`probe_dbfail.py timeout` 探针：conn_a 持
  `LOCK TABLE tasks IN ACCESS EXCLUSIVE MODE` 后 engine_b 的 acquire 阻塞等待）、
  1 条 103.5s（修复轮全量回归/长时命令，命令实际完成）。
  其余 12 条 Shell 失败为 1–2s 瞬时；22/24 条 Read 失败 <10ms 瞬时
  （fail-closed 文本扫描族，另见 EXP-20260827-001 / EXP-20260823-003）。
- 上下文：Windows PowerShell + uv run；M14 复审需要大量真实 PostgreSQL
  探针与 pytest，前台长命令频繁跨过执行通道超时。
- 影响：67s 系把"命令实际还在跑"误判为"命令失败"会错误进入诊断；
  262s 系探针设计错误（持锁后不释放、无超时保护）导致会话阻塞，
  需进程级清理。

## Solution

- 根因：
  1. 67s 族：`uv run` 冷启动 + pytest 收集/执行在 Windows 上单条命令
     总时长经常 >60s；执行通道对前台命令的等待上限导致返回 CURSOR_ERROR，
     但命令在终端内继续执行（terminals 文件可确认）。
  2. 262s 族：探针自身缺陷——`LOCK TABLE` 不释放 + 无 statement_timeout/
     后台化，engine 的 acquire_lease 无超时保护，双方互等。
- 解法（稳定模式）：
  1. 预期 >60s 的命令一律后台化：`block_until_ms: 0` + 读 terminals 文件
     确认状态与 exit_code（EXP-20260814-002 既有模式），或拆小命令；
  2. 前台长命令返回 CURSOR_ERROR 且 duration 接近通道上限时，先读
     terminals 文件确认命令是否仍在跑/已完成，不直接当失败重跑；
  3. 写 PostgreSQL 锁/互等类探针时必须自带释放路径与超时
     （`SET statement_timeout` 或 `try/finally rollback`），并后台化执行；
     已挂起时用 `Stop-Process -Id <pid> -Force` 杀进程树，残留 DB 会话用
     `SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE ...`
     清理（本会话实测可行）。
- 被拒方案：对 67s 命令盲目重跑（可能双跑 pytest）；对 262s 挂起仅杀
  python 进程不清理 PG 会话（残留 active 锁会话继续阻塞后续测试）。

## Evidence

- source_refs：上述 observation 文件（Shell 读取成功）；本会话 terminals
  输出与 `pg_stat_activity`/`pg_terminate_backend` 执行记录。
- 如何失效：执行通道提升前台等待上限、或 uv 冷启动加速后，67s 族不再
  触发；探针若统一后台化 + 自带超时，262s 族不再出现。
