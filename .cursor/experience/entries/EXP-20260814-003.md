# learning eval 脚手架 build() 必须构造隔离骨架，不复制真实资产（fixture 污染）

## Problem

- 现象：`run_cursor_learning_evals.py` 持续 FAIL，`valid` 模式报
  `proposal missing registry entry: LEARN-20260813-001/002` 与
  `promoted target path does not exist: .cursor/rules/42-command-encoding.mdc`，
  但真实 REGISTRY.yaml 与 proposal 文件均正常（`validate_cursor_learning`
  单独运行 PASS）。
- 上下文：`build()` 用 `shutil.copytree(ROOT/'.cursor/learning', ...)` 把
  真实 LEARN 资产复制进临时目录，随后 `install()` 将 REGISTRY.yaml 的
  `entries` 整体替换为 fixture 条目——真实提案文件留在临时目录但 registry
  里消失；且真实提案 target_paths 指向 `.cursor/rules/`，临时目录未复制
  rules。仓库在首个 LEARN proposal 晋升（2026-08-13）前 eval 正常，晋升后
  即开始 FAIL。
- 影响：m0 profile 中 framework/run_cursor_learning_evals 红灯，且错误
  信息指向真实资产，容易被误判为"LEARN proposal 资产损坏"。

## Solution

- 根因：eval 脚手架 fixture 与仓库真实资产混装（fixture 污染）。单次观察，
  未经独立复现。
- 解法：`build()` 不再复制真实 `.cursor/learning/`，改为构造最小隔离骨架：
  空 inbox/accepted/rejected/clusters 目录 + 复制 SKILL_RELATIONS.yaml +
  从 framework.json 读取 framework_version 生成空 entries 的 REGISTRY.yaml。
  eval 只测自身 fixture 逻辑，与仓库资产解耦。
- 被拒方案：修改 `install()` 为"追加" entries（真实提案 target_paths 仍
  会触发 rules 缺失错误，污染残留）；直接修改真实 LEARN 资产（资产本身
  无问题，validator 单独运行 PASS）。

## Evidence

- source_refs：修复前后 `run_cursor_learning_evals.py` 输出对比
  （FAIL → PASS，2026-08-14）；`validate_cursor_learning.py` 修复前后均
  PASS（真实资产无问题）。
- 如何失效：eval 脚本改为在独立 venv/container 运行、或 build() 被替换
  为共享 fixture 库时本条不再适用。

## 备注

- 本条是经验缓冲，不是工程事实；occurrences=1（单会话观察）。
- 通用模式：任何在临时目录运行 validator 的 eval/测试脚手架，build()
  必须与仓库真实资产隔离，否则 install 阶段的覆盖会污染 fixture 断言。
- 跨会话再现时由 capture-learning 生成 LEARN proposal。
