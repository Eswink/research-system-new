# live relay E2E 必须用环境变量构造真实 endpoint 与模型名，不能复用假 URL fixture

## Problem

- 现象：`tests/e2e/test_m12_usage_real_relay.py` live 分支（requires_live_llm）首次实跑失败
  两次：① `RelayHTTPError: transport error: [SSL: UNEXPECTED_EOF_WHILE_READING]`；②
  `HTTP 503: model_not_found: No available channel for model relay-model`。第三次修复后
  3 passed（离线 2 + live 1）。对应本会话 4 条 Shell CURSOR_ERROR（3.7–9.4s，调试期命令）。
- 上下文：M12 DoD-3 真实凭据闭环（`LLM_MAIN_KEY` 提供后执行 live relay 验证）；
  Windows PowerShell + uv run；真实 relay 为 `apihub.agnes-ai.com/v1` + `agnes-2.5-flash`。
- 影响：live E2E 若误用假 URL fixture 会请求 `relay.example.com`（假域名）产生 SSL EOF
  误导性失败；模型名不对产生 503 model_not_found——两者都把"测试代码缺陷"伪装成
  "relay/凭据问题"，浪费诊断。

## Solution

- 根因：
  1. live 分支误用 `tests.contracts.fixtures.endpoint()`（`base_url=https://relay.example.com/api/v1`
     假 URL）——请求打到假域名，SSL EOF 是假 URL 的 DNS/TLS 失败，不是 relay 问题；
  2. `_request()` 硬编码模型 `relay-model`，真实 relay 只有 `agnes-2.5-flash`——503 是
     请求了不存在的模型。
- 解法（稳定模式）：
  1. `requires_live_llm` 分支一律用环境变量构造真实 `LLMEndpoint`：
     `LLMEndpoint(id=..., protocol="OPENAI_COMPATIBLE", base_url=os.environ["RESEARCHOS_LIVE_E2E_ENDPOINT"], credential_ref="RESEARCHOS_LIVE_E2E_KEY")`；
  2. 请求模型名参数化（`_request(model=...)`），live 分支传真实模型名，离线 MockTransport
     分支保持 `relay-model`（handler 断言 authorization 头，不依赖模型名）；
  3. 环境变量缺失时 `pytest.skip`（既有门控），缺失时先确认凭据/模型名是否与契约
     `examples/config/llm_endpoints.yaml`/`models.yaml` 一致。
- 被拒方案：把假 URL fixture 当"relay 不可达"诊断（浪费时间）；在测试里硬编码真实
  endpoint/凭据（泄漏 secret，违反凭据不落盘约束）。

## Evidence

- source_refs：本会话 observations（4 条 Shell 签名见 frontmatter）；`tests/e2e/test_m12_usage_real_relay.py`
  修复后 3 passed（2026-08-28 实测）；`tools/m12_relay_smoke.py` probe ok=True（同凭据对照）。
- 如何失效：若 fixture `endpoint()` 改为可注入真实 base_url，或 live E2E 改为从契约
  加载 endpoint，本条"必须手动构造真实 endpoint"的步骤不再需要；若凭据/模型名变化，
  仍需按契约同步。
