# uv add/sync/install 在 Windows 卡死且文件系统验证证明未完成：lock 拆步 + wheel 手动解压应急路径

## Problem

- 现象：`uv add`、`uv sync --frozen --dev`、`uv pip install --no-index <本地 wheel>` 在 Windows PowerShell 前台长等待（120s-300s）下全部返回 shell-incomplete；`Get-Process uv` 反复查无进程（进程被终止）；`terminals` 目录无对应状态文件。
- 上下文：M9 会话引入新依赖 docker==7.2.0；uv 0.11.18；同会话 `uv lock` 单独运行 7.9s 秒级完成（Resolved 144 packages in 5.57s）；`Test-Path .venv\Lib\site-packages\docker` → False。
- 影响：依赖安装/同步步骤 4 次 attempt 卡死（含一次本地 wheel 离线安装），阻塞容器测试前置；与 EXP-20260814-006 的关键差异——本会话文件系统验证证明命令**没有**完成，不能按"命令实际完成"继续。
- 关键事实：`uv lock`（纯解析、输出少）始终秒级成功；卡死均发生在需要写环境/下载的 add/sync/install 步骤。

## Solution

- 根因：单次观察，未经独立复现——uv 写环境/下载步骤在本机长等待下进程被反复终止，且无任何流事件回传；无法定位是终端会话、杀软还是 uv 内部问题。
- 解法（分流前置：先用文件系统验证，False → 走本路径）：
  1. 依赖变更拆步：手动 PatchEdit `pyproject.toml`（精确 pin）+ `uv lock`（秒级成功）——本会话成功。
  2. 安装用手动解压：curl 下载 wheel → 复制为 `.zip` → `Expand-Archive -Path x.zip -DestinationPath .venv\Lib\site-packages -Force`（纯 Python 无编译包直接可用）→ `uv run python -c "import <pkg>"` 验证（本会话 docker 7.2.0 验证成功，容器测试全绿）。
- 被拒方案：反复重试 uv add/sync（同签名反复超时 + 进程被杀）；`uv pip install --no-index 本地 wheel`（同样卡死）。
- 与 EXP-20260814-006 的分流：先文件系统验证——True → 按 EXP-006 继续（命令实际完成）；False → 按本条目应急路径（lock 拆步 + wheel 解压）。

## Evidence

- source_refs：本会话终端输出（4 次 shell-incomplete + uv lock 秒级成功对照 + Test-Path False + Expand-Archive True + import 验证）；`pyproject.toml`/`uv.lock` 中 docker==7.2.0 已正确 pin；后续 m0 profile 全绿（1298 pytest 含容器测试）。
- 如何失效：Cursor 终端流通道或 uv 行为变化后不再需要此变通；切换到 Linux 时本条目大概率不适用。
