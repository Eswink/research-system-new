# uv add/sync 前台等待返回 shell-incomplete 但命令实际完成：拆 lock 步骤 + 文件系统验证

## Problem

- 现象：`uv add "mcp>=1.28,<2"` 与 `uv sync` 在前台长等待（60s-600s）下全部返回 `Missing terminal shell stream event (expected exit or backgrounded)`；多次重试（`--no-sync`、输出重定向到日志文件、`cmd /c` 包裹）均同签名失败，且 `terminals` 文件夹为空（连终端状态文件都没有，无法读取后台状态）。
- 上下文：M8 会话首次引入新依赖（mcp + 其传递依赖）需下载解析；Windows PowerShell；uv 0.11.18；同会话 `uv lock` 单独运行仅 4.1s 秒级完成。
- 影响：同会话 ≥8 次 attempt 超时（120s/60s/240s/60s/600s/10s/120s/180s），浪费大量等待时间；实际命令其实已在后台完成（文件系统验证确认），只是流事件未回传。

## Solution

- 根因：单次观察，未经独立复现——uv add/sync 的前台终端流事件未回传（重定向到文件时日志文件也未被创建，说明整个流通道丢失），但 uv 进程实际继续运行并完成；输出极少的 `uv lock` 反而正常返回。
- 解法：
  1. 依赖变更拆两步：手动编辑 `pyproject.toml`（PatchEdit）+ `uv lock`（秒级完成、纯解析输出少）——本会话成功路径（Resolved 143 packages in 2.58s）。
  2. 安装/同步状态用文件系统验证：`Test-Path .venv\Lib\site-packages\<pkg>` 或 `uv run python -c "import <pkg>; print(<pkg>.__file__)"`；不要依赖终端流事件判断成败。
  3. 若必须跑 `uv sync`：接受 shell-incomplete 结果后先验证文件系统再继续，不反复重试。
- 被拒方案：反复重试 uv add/uv sync（同签名反复超时）；`*> log` 输出重定向（日志文件根本未创建，重定向被流丢失吞掉）；`cmd /c` 包裹（无效）。

## Evidence

- source_refs：本会话终端输出（≥8 次 shell-incomplete + uv lock 秒级成功对照 + Test-Path True 验证）；`uv.lock` 中 mcp==1.29.0 已正确锁定。
- 如何失效：Cursor 终端流通道修复（事件正常回传）或 uv 版本行为变化后不再需要此变通。
