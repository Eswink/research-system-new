## 做了什么

在 GOAL-023 EC-01 里，规范页新增了一节 `## 标准收口断言集`，判据断言「该小节**点名**了断言集文件」
（`tools/closeout_recheck_assertions.py`），并按 **AST** 复核「被点名的那个文件真的声明了
`standard_verdicts`」。按键压流程去按压它时，**第一次按压无效**：只把**条款句**里那一处点名
改掉，判据仍然 `6 passed`；直到把该小节里**两处**出现（条款句 + 用法 `bash` 片段）**都**改掉，
才得到 `2 failed, 4 passed`。

## 为什么这样做

一次按压「没红」有两种截然不同的原因：**(i) 判据写错了（它根本不在判那个东西）**；
**(ii) 判据是对的，但被按压的对象还有另一条路可以满足它**。第一种要改判据，第二种要**改按压**。
把两者混在一起，就会得出错误的结论 —— 要么误判「判据是空壳」，要么**误判「判据已被按压过」**
而把一个从未被有效按压的判据当成已验证。

具体到这个形态：判据的谓词是「`X in section_text`」。section 是**一整节的文本**，
只要该节里**任何一处**提到 X，谓词就为真。于是「改掉一处」在语义上是**改文案**，
不是**抽走点名** —— 判据正确地保持为绿。**按压必须与被按压的谓词的量词对齐**：
谓词说「存在一处」，按压就要让「**所有**出现」都消失（然后再逐字节复原）。

## 怎么做与复现

1. 先数出现次数：`grep -c '<被点名路径>' <文档>`；再把范围收进那一节，确认节内出现数。
2. 按压时把**节内的每一处**都改写掉（用 Edit 工具；本仓 Bash 直接写源码会被安全扫描拒绝）。
3. 只有在「节内出现数 **0**」的状态下判据仍为绿，才可以判定**判据是空壳**（形态 (i)）。
4. 复原后**必须**用 raw `sha256` 复核逐字节一致（**不得**用 `git diff` 充当该证据 ——
   `.gitattributes` 归一化会掩掉行尾差异），再复跑一次确认转绿。
5. 记按压结论时**写明改了几处**：只说「按压过 ⇒ 判红」会掩盖「哪一处才是真正被断言的」。

复现观察（GOAL-023 EC-01 实测）：只改条款句 ⇒ `6 passed`（**按压无效**）；
条款句 + 用法片段都改 ⇒ `2 failed, 4 passed`（有效）；复原后 raw `sha256` 回到原值 ⇒ `23 passed`。

## 适用边界

- 适用于**任何「文本里存在 X」形态的文档面判据**（「条款不得悬空」「清单点名」「锚点在位」）。
- **不适用于**行为判据（跑出来的判词、返回码、结构化字段）：那些谓词本身就是执行结果，
  按压方式是破坏**执行**，不是改文本。
- 本条的判定标准是「节内出现数」；若将来判据改成「**恰好一次**」（如
  `test_control_plane_auth_same_source.py` 的同源句断言），则按压「改一处」就足以翻转 ——
  **按压形态要跟着谓词的量词走**，没有一种按压形态是普遍有效的。
- 本条只是**过程纪律**，不是对抗性控制：它不阻止有人同时改判据与文档。
